### 1. The Phenomenon

A function that takes 4 milliseconds in a benchmark takes 23 milliseconds in production. A surgeon who ties a knot in 8 seconds in the simulation lab takes 14 seconds in the operating room. A developer who fixes a bug in 20 minutes when working alone takes 55 minutes during a regular workday with messages, meetings, code reviews, and context switches. A single-threaded program that completes in 100 milliseconds takes 340 milliseconds when running alongside three other processes on the same machine.

Nothing is wrong with the processor in any of these cases. The function is the same function. The knot is the same knot. The bug is the same bug. The program is the same program. The processor's capability has not degraded. What changed is the environment,  other activities are competing for shared resources. The work itself is identical. The overhead is the difference, and the overhead is large.

This overhead has names in every domain. In computing it is called contention. In organizations it is called coordination cost. In cognitive science it is called task-switching cost. In manufacturing it is called changeover time. Each domain has its own vocabulary and its own local models for why things take longer than they should. None connects to the others. The computing models use queueing theory. The cognitive models use attentional resource theory. The organizational models use communication complexity. Each explains its own domain and is silent on the rest.

This paper formalizes the overhead as a single computable quantity derived from system structure,  the topology of shared resources and competing activities,  applicable across all domains. The tool is a graph. The result is an equation.

The vocabulary is small and builds in order. Processing is what any system does when it must act on information,  a CPU executing instructions, a surgeon operating, a pilot flying, a developer debugging. The unit of processing is the **op**: one irreducible transformation by one processor. Processing entropy is the op count a specific processor requires for a specific task. The processor's total capacity is bounded by one inequality: total ops multiplied by average op duration must not exceed the available time budget.

Two counting regimes apply to any processing measurement. The **isolated regime** measures one task on one pipeline with no concurrency,  nothing else running, no competition, no interruption. This is where the theoretical minimum cost lives: the ops required for the task itself and nothing else. The **in situ regime** measures the same task in its real execution environment,  other tasks competing for the same pipeline, shared resources occupied by others, and the full weight of the concurrent world pressing on the processor.

The difference between in situ cost and isolated cost is the **concurrency tax**: additional ops, inflated op durations, and dead time generated by the execution environment rather than by the task itself. This paper shows that the concurrency tax is derivable from the structure of the system,  from which resources are shared and which activities compete for them,  rather than being an empirical quantity that can only be measured after the fact.

### 2. The Five Components

The concurrency tax is not one thing. It is five distinct phenomena that sum to the total overhead. Each has a different mechanism, a different scaling behavior, and a different intervention strategy. Treating them as one undifferentiated "overhead" obscures the structure that makes the tax computable.

**Contention.** A processing stream needs a resource that another stream currently holds. The needing stream waits. The wait consumes time budget without producing work. The op itself is unchanged,  same transformation, same logical content,  but its duration inflates by the waiting time. A database query blocked on a connection pool slot occupied by another query still executes the same query when the slot opens. The query cost hasn't changed. The calendar time has. A surgeon waiting for an instrument currently in the assistant's hand still ties the same knot when the instrument arrives. The knot cost hasn't changed. The operating time has. Contention inflates op duration without increasing op count.

**Cascade.** Activity by one stream changes the context experienced by another stream, invalidating dissolved processing and promoting it back to active cost. Prior work in this series established that dissolved tasks have validity envelopes,  regions of context within which dissolution holds. When a competing stream's activity pushes context outside those envelopes, dissolved tasks promote back to active processing, adding ops that would not exist in isolation. A context switch on a CPU evicts cache entries: each subsequent access that would have been a 4-cycle dissolved lookup becomes a 200-cycle active memory fetch. An interruption in the operating room breaks the surgeon's dissolved instrument-handling rhythm, requiring conscious re-engagement with a task that was costing zero. A Slack notification ejects the developer's dissolved codebase navigation from working memory, requiring reconstruction. Cascade adds ops to a stream that the stream would not have generated on its own.

**Coordination.** Ops spent managing the concurrency itself,  not advancing any stream but maintaining the conditions under which concurrent streams can coexist. Lock acquisition and release. Team communication protocols. Handoff confirmations. Status updates. Merge conflict resolution. These ops exist only because concurrency exists. In the isolated regime, there is nothing to coordinate. Every coordination op is pure overhead,  it advances no task, produces no output, and exists solely to manage the interaction between streams that are themselves trying to produce output.

**Blocking.** Duration where the pipeline is idle because it cannot proceed until a resource held by another stream becomes available. Unlike contention (where the op duration inflates but the pipeline is occupied by the waiting op), blocking is dead pipeline,  no op is executing, no transformation is occurring, and time budget is consumed at zero work output. A thread sleeping on a lock is blocking. A surgeon paused while waiting for a frozen section result is blocking. A developer waiting for CI pipeline completion is blocking. The distinction from contention matters because contention inflates an op's measured duration while blocking inserts dead time between ops. Both consume time budget, but they respond to different interventions.

**Interleave.** Ops spent deciding which stream to service when multiple streams are ready for attention. The meta-decision about what to work on next. When only one stream exists, there is no decision,  the pipeline processes whatever is next in that stream. When multiple streams compete, the pipeline must choose: which thread to schedule, which request to handle, whether to respond to the message or continue the current task. The choice itself is an op (or multiple ops for complex priority calculations), and it advances no stream. The scheduler's algorithm for choosing the next process. The surgeon's judgment about whether to address the nurse's question or finish the current suture. The developer triaging between the Slack message, the code review request, and the bug they were investigating. Each interleave decision consumes pipeline capacity that could have been spent on actual work.

The total concurrency tax for a stream is the sum:

tax = contention + cascade + coordination + blocking + interleave

In the isolated regime, all five terms are zero,  there are no other streams, no shared resources, no context disruption, nothing to coordinate, nothing to choose between. In situ, each contributes some positive amount. The question is whether those amounts are computable from the system's structure before the system runs.

### 3. The Contention Graph

The system's structure,  which resources are shared and which streams compete for them,  is a graph. Making the graph explicit makes the concurrency tax derivable.

Define the **contention graph** G = (R, S, E) with three components.

**R = {r₁, r₂, ..., rₘ}** is the set of shared resources. A shared resource is anything that serves one stream at a time or degrades when serving multiple streams simultaneously. In computation: a CPU core, a cache line, a memory bus, a database connection pool slot, a disk I/O channel, a network socket. In surgery: a specific instrument, the surgeon's visual focus, the circulating nurse's hands, the anesthesia monitor's attention, the operative field itself. In an office: a meeting room, the CI pipeline, the team lead's decision-making capacity, a shared document under concurrent editing, the deployment environment.

**S = {s₁, s₂, ..., sₙ}** is the set of processing streams. A stream is a sequence of ops that constitutes one logical task being executed concurrently with others. In computation: a thread, a process, a request being handled. In surgery: the primary procedure, patient monitoring, instrument management, anesthesia management, documentation. In an office: each developer's current task, each ongoing code review, each active conversation thread.

**E ⊆ S × R** is the set of edges connecting streams to resources. An edge (sᵢ, rⱼ) means stream sᵢ requires resource rⱼ at some point during its execution. Each edge carries three annotations:

**Hold duration** h(sᵢ, rⱼ): how long stream sᵢ holds resource rⱼ per access. A database query holds a connection for the query duration. A surgeon holds an instrument for the duration of its use. A developer holds the CI pipeline for the duration of a build.

**Access frequency** f(sᵢ, rⱼ): how often stream sᵢ requires resource rⱼ per unit time. A process accesses L1 cache thousands of times per millisecond. A surgeon reaches for the primary instrument tens of times per minute. A developer pushes to CI a few times per day.

**Criticality** c(sᵢ, rⱼ): whether stream sᵢ blocks completely when resource rⱼ is unavailable (critical = 1) or can proceed with degraded performance or alternative resources (critical = 0, or a continuous value between). A thread requiring a mutex cannot proceed without it,  critical. A developer waiting for a code review can switch to another task,  non-critical but with switching cost.

The contention graph makes competition structure visible. Two streams that share no resource neighbors cannot contend,  they run as if isolated regardless of how many other streams exist. Two streams connected to many common resources contend frequently. A resource connected to many streams is a bottleneck,  it mediates contention among all its connected streams. A stream connected to many resources is a high-exposure participant,  it has many channels through which other streams can affect it.

The **resource contention degree** of resource rⱼ is the number of streams connected to it: deg(rⱼ) = |{sᵢ : (sᵢ, rⱼ) ∈ E}|. A resource with degree 1 is private,  no contention possible. A resource with degree n (connected to every stream) is maximally shared.

The **stream exposure** of stream sᵢ is the number of resources it requires: exp(sᵢ) = |{rⱼ : (sᵢ, rⱼ) ∈ E}|. A stream with exposure 1 uses one shared resource,  its contention surface is minimal. A stream with high exposure uses many shared resources,  it has many points at which other streams can interfere.

The **contention overlap** between streams sᵢ and sⱼ is the number of resources they share: overlap(sᵢ, sⱼ) = |{rₖ : (sᵢ, rₖ) ∈ E ∧ (sⱼ, rₖ) ∈ E}|. Zero overlap means the streams cannot directly contend. High overlap means frequent potential for interference.

### 4. Deriving Tax Components from Graph Properties

Each component of the concurrency tax is a function of the contention graph's structure and annotations. This section derives each one.

**Contention cost.** For resource rⱼ with degree k (shared by k streams), the probability that a stream finds it occupied depends on the aggregate demand. Each connected stream sᵢ generates demand at rate f(sᵢ, rⱼ) with hold duration h(sᵢ, rⱼ). The utilization of resource rⱼ is:

ρ(rⱼ) = Σᵢ f(sᵢ, rⱼ) × h(sᵢ, rⱼ)

summed over all streams connected to rⱼ. When ρ < 1, the resource is below saturation and contention is probabilistic,  sometimes available, sometimes occupied. When ρ ≥ 1, the resource is saturated and contention is guaranteed,  streams queue.

For the subsaturation regime, model resource rⱼ as a single server with aggregate arrival rate λⱼ = Σᵢ f(sᵢ, rⱼ) and mean service time μⱼ⁻¹ = mean of h(sᵢ, rⱼ) across connected streams. The expected waiting time per access, from standard queueing results, is:

W(rⱼ) = ρ(rⱼ) / (μⱼ × (1 − ρ(rⱼ)))

This is the M/M/1 waiting time, applicable when arrivals are approximately Poisson and service times approximately exponential. For more structured access patterns, the formula adjusts (M/D/1 for deterministic service, M/G/1 for general service distributions), but the functional dependence on ρ remains: waiting time increases with utilization and diverges as ρ approaches 1.

The total contention cost for stream sᵢ is the sum of expected waiting time across all resources it uses:

contention(sᵢ, G) = Σⱼ f(sᵢ, rⱼ) × W(rⱼ)

Each access to each shared resource contributes its frequency-weighted expected wait. Resources with high utilization contribute disproportionately. Resources with low utilization contribute little.

**Cascade cost.** Stream sᵢ has a dissolution inventory,  a set of dissolved elements with validity envelopes in context space, as developed in prior work. Other streams' activities on shared resources constitute context changes that may violate those envelopes.

Define the **cascade coupling coefficient** κ(sᵢ, sⱼ, rₖ) as the expected number of cascade promotions in stream sᵢ per unit of activity by stream sⱼ on shared resource rₖ. This coefficient depends on how much of sⱼ's activity on rₖ falls outside sᵢ's validity envelopes for elements whose dissolution involves rₖ. A context switch on a CPU where two processes share L1 cache has a high κ because the incoming process's memory accesses evict the outgoing process's cached data. Two processes sharing a database connection pool but accessing different tables have low κ because holding a connection doesn't change the other process's processing context.

The total cascade cost for stream sᵢ is:

cascade(sᵢ, G) = Σⱼ≠ᵢ Σₖ κ(sᵢ, sⱼ, rₖ) × activity(sⱼ, rₖ) × recovery_cost(sᵢ)

where activity(sⱼ, rₖ) is stream sⱼ's usage rate of shared resource rₖ, and recovery_cost(sᵢ) is the average op cost to restabilize a promoted element in stream sᵢ. The triple sum reflects that cascade damage to stream sᵢ comes from every other stream through every shared resource, weighted by the coupling coefficient.

**Coordination cost.** Each shared resource may require coordination ops to manage concurrent access. Define coord(rⱼ) as the coordination cost per access to resource rⱼ,  the ops required for acquisition protocol, release protocol, and state consistency verification. For a mutex: the lock and unlock operations. For a surgical instrument: the request, confirmation, and handoff. For a code review: the request, review cycle, and merge protocol.

The total coordination cost for stream sᵢ is:

coordination(sᵢ, G) = Σⱼ f(sᵢ, rⱼ) × coord(rⱼ)

Every access to every shared resource incurs its coordination cost. Resources with expensive protocols contribute more. Resources accessed frequently contribute more.

**Blocking cost.** When resource rⱼ is critical for stream sᵢ (criticality c(sᵢ, rⱼ) = 1) and rⱼ is occupied, the stream blocks,  pipeline is idle, time budget consumed, zero ops executed. The blocking cost is the expected time spent blocked:

blocking(sᵢ, G) = Σⱼ f(sᵢ, rⱼ) × c(sᵢ, rⱼ) × W(rⱼ)

This is similar to contention cost but applies only to critical-path resources (weighted by criticality) and represents dead time rather than inflated op duration. For non-critical resources (c = 0), the stream can switch to another activity during the wait,  the cost shifts from blocking to interleave.

**Interleave cost.** When the pipeline must choose between ready streams, the choice consumes ops. Define interleave_cost(k) as the op cost of choosing between k ready streams. For a simple round-robin scheduler: interleave_cost ≈ constant (one op regardless of k). For a priority-based scheduler: interleave_cost = O(log k) (priority queue operations). For a complex multi-criteria decision (the surgeon evaluating whether to respond to the nurse): interleave_cost may be several ops involving evaluation of urgency, current task interruptibility, and consequence assessment.

The total interleave cost for stream sᵢ depends on how often it is preempted or must choose, which depends on the arrival rate of competing demands:

interleave(sᵢ, G) = preemption_rate(sᵢ, G) × interleave_cost(active_streams(G))

where preemption_rate is how often stream sᵢ is interrupted by a competing stream, and active_streams is the number of concurrent streams ready for the pipeline.

### 5. The Concurrency Tax Equation

The total concurrency tax for stream sᵢ in contention graph G assembles all five components:

tax(sᵢ, G) = contention(sᵢ, G) + cascade(sᵢ, G) + coordination(sᵢ, G) + blocking(sᵢ, G) + interleave(sᵢ, G)

The in situ cost of stream sᵢ is:

cost_insitu(sᵢ) = cost_isolated(sᵢ) + tax(sᵢ, G)

The total system cost across all streams is:

cost_total(G) = Σᵢ cost_isolated(sᵢ) + Σᵢ tax(sᵢ, G)

The tax has several structural properties that follow from the derivations.

**The tax is a system property, not a stream property.** Each stream's tax depends on every other stream through shared resources. Adding a stream increases every other stream's tax: more contention on shared resources, more cascade risk from context changes, more coordination per access, more blocking from occupied resources, more interleave decisions when the pipeline chooses. The tax is computed from the graph, not from any stream in isolation.

**The marginal tax of the (k+1)th stream is generally superlinear.** Each additional stream adds tax to every existing stream. The k+1th stream contends with k existing streams on shared resources, generates cascade coupling with k streams, adds coordination ops for k potential interactions, adds blocking probability for k competitors, and adds one more option to every interleave decision. The total tax increase from adding one stream grows with the number of existing streams.

**The tax dominates at high concurrency.** When the number of streams is small relative to the number of resources, tax is small,  most resources are uncontested, cascades are rare, coordination is light. As stream count increases, utilization rises, contention increases nonlinearly (the queueing wait time diverges as ρ → 1), cascades become frequent, coordination accumulates, blocking becomes common, and interleave decisions become continuous. At some stream count, the tax per stream exceeds the stream's isolated cost,  concurrency overhead exceeds useful work. Beyond this point, adding streams decreases total throughput.

**The tax structure determines the intervention.** Contention-dominated tax responds to resource replication. Cascade-dominated tax responds to isolation and wider dissolution envelopes. Coordination-dominated tax responds to protocol simplification and dissolution of coordination routines. Blocking-dominated tax responds to asynchronous design. Interleave-dominated tax responds to scheduling policy. Diagnosing which component dominates,  which requires the component decomposition, not just the total,  determines which intervention works.

### 6. Architectural Motifs

Certain contention graph topologies recur across domains. Each has a characteristic tax profile derivable from its structure.

**Star topology.** One central resource connected to all streams. All contention concentrates on one point. The central resource has degree n (all streams), utilization ρ = n × f̄ × h̄, and waiting time that diverges as ρ → 1. Peripheral resources (if any) are private,  no contention.

Tax is dominated by contention and blocking on the central resource. As stream count increases, the central resource saturates. The tax scaling is steep: O(n/(1−nfh̄)) for contention, approaching divergence as nf̄h̄ → 1.

Examples: single database connection pool serving all application threads. Single CI pipeline shared by all developers. Single meeting room for all teams. Surgeon's visual attention as sole shared resource during complex multi-participant procedures. In each case, the central resource is the system's throughput ceiling.

Mitigation: replicate the central resource. Multiple connection pools. Parallel CI runners. Multiple meeting rooms. A second surgeon or an assistant with independent visual field. Replication transforms the star into a partitioned or hierarchical topology.

**Chain topology.** Resources shared pairwise along a sequence. Stream 1 shares resource A with stream 2. Stream 2 shares resource B with stream 3. Stream 3 shares resource C with stream 4. No stream shares a resource with a non-adjacent stream.

Tax propagates along the chain. A delay in stream 1 holds resource A, blocking stream 2, which holds resource B, blocking stream 3. The propagation delay through a chain of length L accumulates: total propagation time is the sum of individual contention delays, which can amplify small initial delays into large end-to-end latencies.

Cascade coupling is nearest-neighbor only,  a stream can only be disrupted by the streams it shares resources with. Coordination is pairwise. Blocking propagates sequentially.

Examples: pipeline architectures where each stage hands output to the next through a shared buffer. Assembly lines where stations share tooling with adjacent stations. Sequential approval chains where each approver's output is the next's input.

Mitigation: buffer between chain links (decouples propagation), parallel chains (redundancy), or asynchronous handoff (converts blocking to non-blocking).

**Complete graph (all-to-all).** Every stream shares at least one resource with every other stream. Maximum contention topology.

Tax scales quadratically. Every pair of streams can contend on shared resources. Adding the (k+1)th stream adds k new contention relationships. Total coordination overhead is O(n²) because every pair may need to coordinate. Cascade exposure is maximal,  every stream's activity can disrupt every other stream.

Examples: shared-everything symmetric multiprocessor architectures. Open-plan offices where every person can see and interrupt every other person. Team meetings where every participant speaks to every other. Shared mutable state accessed by all threads.

This topology produces the maximum possible concurrency tax for a given stream count. The tax dominates quickly,  useful throughput peaks at a low stream count and degrades beyond it.

Mitigation: partition. Divide streams into groups that share resources within groups but not between. Transform the complete graph into a partitioned topology.

**Partitioned topology.** Streams divided into groups of size k. Resources shared within groups but not between. No inter-group edges.

Tax is bounded by within-group contention. Each group experiences tax as if it were a system of k streams. Groups are independent,  adding streams to one group does not affect another. Total tax scales with group size k, not total stream count n.

Examples: NUMA domains where each processor group has its own memory controller. Pod-based team structures where each pod has its own resources and communicates with other pods only through defined interfaces. Microservice architectures where each service manages its own state.

This topology achieves linear scaling with total streams as long as group size is bounded. The cost is that cross-group work requires inter-group coordination (a new type of coordination cost at a higher level), but within-group work is insulated from the rest of the system.

**Hierarchical topology.** Resources organized in tiers. Local resources (private or small-group) are cheap to access and rarely contested. Global resources (system-wide) are expensive and highly contested. Streams access local resources frequently and global resources rarely.

Tax has two components: low local tax (frequent access, low contention) and high global tax (rare access, high contention). The effective tax is dominated by the access frequency distribution,  if most accesses are local, the tax is low despite high global contention.

Examples: CPU cache hierarchies. L1 private (zero contention), L2 shared by core pair (low contention), L3 shared by all cores (moderate contention), main memory (high contention). Organizational hierarchies: team-level decisions (fast, uncontested), department-level decisions (slower, some contention), company-level decisions (slow, high contention). The hierarchy's depth and branching factor determine the tax profile.

Tax scales as O(log n) for the common case (most accesses resolved locally) with O(n) penalties for global access (resolved at the root). The tradeoff is latency versus sharing,  local resolution is fast but isolated, global resolution is slow but coordinated.

### 7. Human and Organizational Processors

The contention graph formalism extends to human processors without modification. The shared resources are cognitive and organizational rather than computational. The mechanisms are the same.

The human processor has one pipeline: conscious attention. It processes one op at a time. Multiple concurrent demands compete for this pipeline. The demands are the streams. The shared resources they compete for include:

**Working memory.** Limited capacity, shared across all active tasks. A developer holding a complex data flow in working memory uses most of the available capacity. An interruption that requires understanding a different context competes for the same memory. Working memory is a high-contention resource with high cascade coupling,  evicting one task's context to load another's invalidates the first task's dissolved processing chains.

**Visual attention.** One focal point at a time. The surgeon's eyes can attend to one location. A notification on screen competes with the code being read. A new instrument in the operative field competes with the tissue being dissected.

**Motor system.** One pair of hands doing one thing. The developer's hands can type one thing. The surgeon's hands can manipulate one instrument. Motor contention is rare for cognitive work (the bottleneck is usually attention, not hands) but common for physical work.

**Communication bandwidth.** One conversation at a time at full attention. The developer can engage with one Slack thread, one meeting, or one code review conversation at full quality. Concurrent conversations degrade all of them.

The contention graph for a developer during a workday maps directly. Streams: primary development task, code review requests, Slack conversations, email, meetings, incident monitoring, administrative tasks. Resources: working memory, visual attention, communication bandwidth, CI pipeline, shared codebase (merge conflicts), team lead's decision capacity. Edges connect each stream to the resources it requires, annotated with hold durations, access frequencies, and criticality.

The tax derivation follows the same equations. Contention cost: how often each resource is occupied by a competing stream when the developer needs it. Cascade cost: how much each interruption disrupts dissolved processing. Coordination cost: ops spent on protocols (meeting agendas, status updates, handoff procedures). Blocking cost: time spent waiting for resources (CI pipeline, code review, decisions). Interleave cost: ops spent deciding which stream to attend to.

The cascade component deserves particular attention for human processors because it is typically the dominant term. When a developer is interrupted, the interruption itself may take two minutes. But the cascade,  the dissolution promotions caused by working memory eviction,  adds 15-25 minutes of recovery time as the developer reconstructs their mental model of the code. The interruption's direct cost (2 minutes of coordination) is small. The cascade cost (15-25 minutes of re-orientation) dominates by an order of magnitude.

The contention graph explains this quantitatively. The primary development task holds working memory as a critical resource with long hold duration (the entire development session). Working memory has a small capacity and a high cascade coupling coefficient,  evicting its contents promotes many dissolved processing chains simultaneously. An interruption that requires working memory (understanding a different context) forces eviction. The cascade severity is the count of promoted elements, which for deep programming work can be high,  the developer has dissolved dozens of code navigation patterns, naming conventions, data flow paths, and state assumptions that all depend on the working memory context being maintained.

The graph also predicts which interruptions are expensive and which are cheap. An interruption that does not require working memory (a timer going off, a brief physical movement) has low cascade coupling,  it doesn't evict working memory contents and therefore doesn't trigger a cascade. An interruption that requires loading a different complex context (switching to a different project's codebase) has maximum cascade coupling,  it evicts everything. The concurrency tax of an interruption is predictable from the edge between the interrupting stream and the working memory resource, specifically from the cascade coupling coefficient on that edge.

For organizational processors, the graph extends one level further. The shared resources are organizational structures: the deployment pipeline, the release schedule, the product roadmap, the team lead's attention. Streams are the concurrent projects or work items the organization is pursuing. The contention graph at the organizational level has the same structure,  resources, streams, edges with annotations,  and the same tax components apply.

The organizational cascade component manifests as organizational disruption. A re-organization (context change) that invalidates team members' dissolved coordination patterns,  who to ask for what, how decisions get made, where to find information,  generates cascade promotions across the organization. Each team member must reconstruct their organizational navigation from active processing. The cascade severity is the count of organizational patterns that promoted across all affected team members, which for a large re-organization can be enormous.

### 8. The Expert Tax Discount

Expertise reduces the concurrency tax. Not because the expert's environment is simpler,  the contention graph is the same,  but because three of the five tax components are themselves processing operations that dissolve through repetition.

**Interleave dissolution.** The decision about which stream to service is itself an op. When it is performed repeatedly in consistent conditions, it dissolves like any other op. The experienced surgeon's decision about whether to address the nurse's question or finish the suture is dissolved,  the decision fires structurally based on the urgency pattern and the task's interruptibility, without conscious pipeline allocation. The novice surgeon must consciously evaluate each interruption: Is this urgent? Can my current step be paused? What are the consequences of each choice? Three to five ops per interleave decision for the novice versus zero for the expert.

**Cascade resistance.** Prior work established that wider validity envelopes reduce cascade severity. Experts have wider envelopes,  their skills dissolved under varied conditions, so context changes stay within envelopes rather than crossing them. The expert developer's codebase navigation survives a brief Slack interruption because the navigation dissolved under conditions that included occasional interruptions. The novice developer's fragile, narrowly-dissolved navigation breaks on the same interruption.

The cascade coupling coefficient κ is lower for the expert on every shared resource edge. The same interruption that promotes five working memory items for the novice promotes one (or none) for the expert. The cascade component of the tax shrinks without any change to the contention graph,  the graph is the same, but the expert's dissolution inventory has wider envelopes.

**Coordination dissolution.** The surgical team that has worked together for years coordinates with fewer ops than a newly assembled team. A glance replaces a sentence. A gesture replaces a verbal instruction. The handoff protocol for passing an instrument has dissolved from an explicit request-confirmation-transfer sequence (five ops) to an implicit anticipation-extend-accept sequence (one op or zero if fully dissolved). The coordination cost per access to the shared resource decreases through dissolution of the coordination protocol itself.

Contention cost and blocking cost do not dissolve meaningfully. If the resource is occupied, the expert waits the same duration as the novice,  waiting is not a skill that improves with practice. The expert may use the wait time more productively (by working on a non-blocked stream without cascade cost, which is itself an interleave dissolution), but the raw wait time is structural.

Define the **tax discount** as the ratio of expert to novice concurrency tax for the same contention graph:

δ(expert, novice, G) = tax(expert, G) / tax(novice, G)

This ratio is less than 1. The discount decomposes by component:

δ_interleave: typically large (experts have dissolved interleave decisions)
δ_cascade: typically large (experts have wider validity envelopes)
δ_coordination: moderate (dissolves with team experience, not just individual)
δ_contention: near 1 (waiting time is structural)
δ_blocking: near 1 (blocking time is structural)

The overall discount is dominated by cascade and interleave in environments with frequent context changes (like the operating room or the developer's workday), and dominated by coordination in environments with high coordination protocols (like surgical teams or military units).

The discount is itself a property of the contention graph,  some graph topologies offer more room for discount than others. A graph with few shared resources has small tax and therefore small discount (there is little overhead to dissolve). A graph with many shared resources and high cascade coupling has large tax and large potential discount. The maximum discount occurs in high-concurrency environments with experienced processors: precisely the conditions where the tax would be crushing for novices.

### 9. Architectural Interventions as Graph Transformations

Every architectural intervention that reduces overhead corresponds to a transformation of the contention graph. Making the transformation explicit makes the expected tax reduction computable before implementation.

**Resource replication** (reduces contention and blocking). Duplicating a shared resource splits one high-degree node into two lower-degree nodes. If resource rⱼ with degree n is replicated into rⱼ' and rⱼ'' with degrees n/2 each, the utilization of each drops: ρ_new = ρ_old / 2. The waiting time drops more than proportionally because the queueing wait time is convex in utilization,  halving utilization more than halves waiting time. The total contention and blocking reduction is computable from the degree reduction and the utilization formula.

Example: replacing a single database connection pool (degree 100, utilization 0.85, wait time 5.7 time units per access) with two pools (degree 50 each, utilization 0.425 each, wait time 0.74 time units per access). The contention reduction is 87%,  not 50%,  because the queueing function is nonlinear.

**Isolation** (reduces cascade). Preventing one stream's activity from affecting another stream's context. In the contention graph, isolation removes cascade coupling coefficients on shared resource edges. Full isolation (separate address spaces, separate working environments) sets κ to zero on all edges between isolated streams. Partial isolation (noise-canceling headphones, cache partitioning) reduces κ without eliminating it.

Example: process-level cache partitioning on a multi-core CPU. Assigning each process a dedicated cache partition eliminates cache eviction cascades between processes. The cascade coupling coefficient κ drops to zero on the L1 and L2 cache edges. The cascade component of the concurrency tax for each process drops to zero for cache-mediated disruption. The total tax reduction is computable from the prior cascade cost on those edges.

**Protocol simplification** (reduces coordination). Reducing the ops required for managing concurrent access to shared resources. In the contention graph, protocol simplification reduces coord(rⱼ),  the coordination cost per access,  on specific resources.

Example: replacing a three-phase commit protocol (6 ops per coordination point) with an optimistic concurrency protocol (1 op per coordination point, occasional retry). The coordination cost per access drops by 5/6. The total coordination reduction across all streams accessing that resource is computable from the access frequency and the per-access cost reduction.

**Asynchronous decoupling** (reduces blocking). Allowing streams to proceed without waiting for resources, deferring the resource need to a later time when it may be available. In the contention graph, asynchronous decoupling changes the criticality annotation on edges from c = 1 (blocking) to c = 0 (non-blocking). The blocking component drops to zero on those edges. The cost shifts to interleave (the stream must decide what to do while waiting) and possibly coordination (tracking the deferred request), but these are typically cheaper than blocking.

Example: replacing synchronous code review (developer blocks until reviewer responds) with asynchronous review (developer switches to another task, reviews arrive as notifications). The blocking cost on the "reviewer attention" resource drops to zero. The interleave cost increases slightly (developer must manage task switching) and cascade cost may increase (switching tasks may evict working memory), but the total tax typically decreases because blocking time is pure dead time while interleave and cascade at least permit some useful work.

**Scheduling policy** (reduces interleave). Replacing deliberative interleave decisions with structural (dissolved) scheduling. In the contention graph, scheduling policy reduces interleave_cost by replacing per-decision evaluation with a pre-computed rule.

Example: a developer adopting time-blocking,  defined two-hour blocks of uninterruptible focus with all notifications deferred to between blocks. The interleave decision within a block is dissolved (the rule is: don't switch). The interleave cost during blocks drops to zero. Between blocks, the developer processes accumulated interruptions in a batch, which is cheaper than individual interrupt-driven responses because the context switches happen at natural boundaries rather than mid-task.

For each intervention, the expected tax change is:

Δtax = tax(sᵢ, G_new) − tax(sᵢ, G_old)

where G_new is the contention graph after the transformation and G_old is the graph before. This is computable from the graph transformation and the tax equation, making the cost-benefit of each intervention evaluable before implementation.

### 10. Computational Test Case

Ground the formalism in a system where every quantity is measurable to the nanosecond.

**Multi-process system on a four-core CPU.** Four processes (P1–P4) running simultaneously on four cores sharing a memory hierarchy.

The contention graph has four streams (P1–P4) and five resources: L1 caches (four private,  degree 1 each, no contention), L2 caches (two shared between core pairs,  degree 2 each), L3 cache (one shared by all four,  degree 4), memory bus (one shared by all four,  degree 4), and memory controller (one shared by all four,  degree 4).

Edge annotations from hardware performance counters during an initial profiling run:

For the L2 cache (shared between P1 and P2): P1 accesses L2 at 50,000 accesses/ms with mean hold time 12 cycles. P2 accesses at 45,000 accesses/ms with mean hold time 15 cycles. Utilization: (50,000 × 12 + 45,000 × 15) / (cycles per ms per L2 bank). The contention cost per access is derivable from the utilization.

For the L3 cache (shared by all four): aggregate access rate and per-process hold times from LLC-reference and LLC-miss counters. Utilization and contention wait derivable from aggregate demand.

For the memory bus: bandwidth utilization from memory controller counters. Contention model as a bandwidth-limited resource rather than a discrete server,  queueing theory applies with capacity as the service rate.

**Cascade measurement.** Run each process in isolation and record cache miss rates. Run all four simultaneously and record cache miss rates. The difference,  additional cache misses in the concurrent run,  is the cascade component. Each additional miss at L2 costs approximately 30 cycles. Each additional miss at L3 costs approximately 200 cycles. The cascade cost in cycles is directly measurable.

**Coordination measurement.** Atomic operations and lock contention visible through hardware contention counters. Each atomic operation has a base cost (a few cycles) that inflates under contention (potentially hundreds of cycles). The coordination cost is the sum of atomic operation costs minus their uncontended baseline.

**Blocking measurement.** Time processes spend in I/O wait or lock sleep, visible through scheduler statistics. Direct measurement of dead pipeline time per process.

**Interleave measurement.** Scheduler overhead measurable through profiling. Time spent in the scheduler's decision code per context switch times number of context switches.

**Prediction versus measurement.** Compute the predicted tax from the contention graph (structure + annotations) using the equations from Sections 4 and 5. Compare against the measured tax (in situ cost minus isolated cost per process). The prediction should approximate the measurement within a bound determined by the accuracy of the queueing model assumptions and the stability of the workload during measurement.

For a secondary validation, introduce architectural interventions and verify predicted tax changes:

Intervention 1: Pin P1 and P2 to cores sharing one L2, P3 and P4 to the other. Predicted effect: reduced L2 contention for the pairs, unchanged L3 and memory contention. Measure and compare.

Intervention 2: Partition L3 cache giving each process a dedicated quarter. Predicted effect: cascade coupling κ drops to zero on L3 edges; cascade component eliminated for L3-mediated disruption. Contention on L3 also eliminated since partitions are private. Measure and compare.

Intervention 3: Reduce P4's priority so it only runs when no other process is ready. Predicted effect: P1–P3 experience near-zero contention from P4; P4's tax increases (it waits for all others). Total system tax may decrease if P4's contribution to others' tax was large. Measure and compare.

Each intervention is a specific graph transformation with a predicted tax change from the equation. The measured change validates (or invalidates) the prediction and calibrates the model for this workload class.

### 11. Organizational Test Case

The contention graph applies equally to human and organizational processors, though measurement is softer. A software development team provides a test case intermediate between precise hardware measurement and purely qualitative organizational observation.

**Team of six developers** working on a shared codebase with shared infrastructure.

The contention graph has six streams (developer work tasks) and six resources: shared codebase (merge conflicts,  degree 6), CI pipeline (build queue,  degree 6), team lead attention (decisions and unblocking,  degree 6), code review pool (each PR needs a reviewer,  degree 6), staging environment (one shared,  degree 6), and meeting time (calendar,  degree 6).

All resources have degree 6,  this is close to a complete graph topology, which predicts high tax. The annotation data comes from existing team tools:

CI pipeline: build duration from CI logs (hold time h), build frequency from commit history (access frequency f), build queue depth (utilization ρ). If average build takes 12 minutes and the team submits 30 builds per day across a 10-hour workday, utilization is 30 × 12 / 600 = 0.6. Expected wait time per build: ρ / (μ(1−ρ)) ≈ 0.6 / ((1/12)(0.4)) ≈ 18 minutes per build.

Code review: time-to-first-review from PR timestamps (wait time), review request frequency from PRs opened per day (access frequency), reviewer availability from calendar analysis. If reviews take an average of 2 hours to begin and developers open 2 PRs per day, the blocking cost is approximately 4 hours per developer per day waiting for reviews,  a third of the workday.

Team lead attention: decision request rate from Slack/email (access frequency), time per decision from interaction logs (hold time), queue depth when multiple developers need attention simultaneously (contention).

Meeting time: total meeting hours per developer per week from calendar (coordination cost), post-meeting recovery time measured by time to first commit after a meeting (cascade cost).

**Predicted tax components.** Contention: primarily CI pipeline (18 minutes per build wait at ρ = 0.6) and code review (2 hours per PR). Cascade: primarily from meeting context switches and Slack interruptions (estimated 15-25 minutes recovery per interruption, 4-6 interruptions per day = 60-150 minutes of cascade per developer per day). Coordination: meetings plus standup plus async communication (estimated 1.5-2 hours per day). Blocking: CI wait plus review wait (estimated 2-4 hours per day). Interleave: task-switching decisions (estimated 15-30 minutes per day).

**Total predicted tax per developer per day:** approximately 4-7 hours. For a 10-hour workday, this leaves 3-6 hours of isolated-equivalent productive work. This matches industry measurements of developer productivity that consistently find 3-5 hours of focused coding per 8-10 hour workday,  the remainder is concurrency tax.

**Intervention predictions.** Adding a second CI runner: transforms star topology on CI resource into two-node partition. Predicted contention reduction on CI: from 18 minutes per build to approximately 4 minutes (utilization halves, wait time drops more than proportionally). Total predicted saving: approximately 30 minutes per developer per day.

Instituting no-meeting mornings: removes meeting stream's edges from the contention graph for half the day. Predicted cascade reduction: half as many meeting-induced cascade events. Predicted saving: approximately 30-60 minutes per developer per day in recovered cascade time.

Switching to async code review with a 4-hour SLA: changes code review from blocking (c = 1) to non-blocking (c = 0). Predicted blocking reduction: 2 hours per developer per day converted from dead wait to productive work on other tasks. Interleave and cascade costs increase modestly (task switching to fill review wait), but net benefit is positive.

Each prediction is testable against before/after productivity metrics,  commit frequency, time to resolution, developer satisfaction surveys, and direct measurement of focused work hours through calendar and tool analysis.

### 12. Predictions

The formalism produces testable predictions across domains.

**Prediction 1: Tax predictability.** The concurrency tax for a given stream is predictable from the contention graph with accuracy proportional to the completeness of edge annotations. Systems with measurable access frequencies, hold durations, and cascade coupling coefficients yield tighter predictions. Systems where these quantities are estimated loosely yield proportionally looser predictions.

**Prediction 2: Intervention specificity.** Architectural interventions that remove edges or reduce edge weights in the contention graph produce measurable reductions in the specific tax components those edges contribute to, and the magnitude is predictable from the graph transformation. An intervention targeting contention reduces contention and does not reduce cascade. An intervention targeting cascade does not reduce contention. The tax equation decomposes the effect.

**Prediction 3: Motif-determined scaling.** The marginal tax of adding the (k+1)th stream follows the scaling law of the graph motif. Star and complete topologies: superlinear. Chain: linear with propagation. Partitioned: constant (within groups). Hierarchical: logarithmic for common case. The scaling law is determined by topology, not by domain.

**Prediction 4: Expert discount components.** Expert concurrency tax is measurably lower than novice tax on the same contention graph. The discount is largest for cascade and interleave (which dissolve through experience) and smallest for contention and blocking (which are structural). Measurable by comparing expert and novice cost on the same tasks in the same concurrent environment.

**Prediction 5: Brooks's Law derivation.** For all-to-all team topologies, total coordination ops grow as O(n²) with team size. At the stream count where marginal coordination tax exceeds marginal isolated work capacity, adding team members decreases throughput. The crossover point is computable from the graph,  specifically from the coordination cost per edge and the edge count growth rate.

**Prediction 6: Optimal concurrency.** For any contention graph, there exists an optimal stream count n* where total throughput (total isolated work minus total tax) is maximized. Below n*, adding streams increases throughput (the new stream's isolated work exceeds its marginal tax). Above n*, adding streams decreases throughput (the marginal tax exceeds the new stream's isolated work). The optimal point is computable from the graph's scaling law: n* = argmax_n { n × work_isolated − tax_total(n, G) }.

### 13. Scope and Open Problems

This paper establishes the contention graph as the structural representation of concurrent system topology, derives the five-component concurrency tax from graph properties, characterizes architectural motifs with their scaling laws, extends the formalism to human and organizational processors, derives the expert tax discount from dissolution of overhead components, and specifies architectural interventions as graph transformations with predictable effects.

The following remain open.

**Dynamic contention graphs.** The graph is treated as static throughout this paper. In practice, streams start and end, resource requirements change, and the graph evolves during execution. Formalizing time-varying contention graphs,  where edges appear and disappear, annotations change, and the tax must be computed as a time-varying function rather than a steady-state quantity,  extends the framework to systems with changing workload mixes.

**Degrading resources.** The formalism assumes resources are either available or occupied. Many real resources degrade continuously under concurrent use rather than blocking: a network link with increasing latency under load, a manager whose decision quality decreases with interruption frequency, a shared codebase where merge conflict probability increases with concurrent edits. Extending the model from binary exclusive access to continuous degradation functions on shared resources would capture these effects.

**Nested contention.** A developer experiences cognitive contention (internal streams competing for working memory) while simultaneously experiencing organizational contention (competing with teammates for shared infrastructure). The two contention graphs interact,  high cognitive tax reduces the developer's output rate, which increases the organizational blocking time for teammates waiting on their deliverables. Formalizing coupled contention graphs at different levels (cognitive, team, organizational) and their cross-level interactions is an open structural problem.

**Component interaction.** The five tax components are summed in the current formulation. In practice, they may interact: high contention increases the probability of cascade (longer waits mean more time for context disruption), high cascade increases interleave cost (more promoted elements competing for the pipeline), and high blocking increases cascade exposure (idle pipeline leaves dissolved elements vulnerable to context change). Formalizing these interactions as second-order terms would improve prediction accuracy for high-load systems.

**Tax measurement standardization.** The paper defines what the concurrency tax consists of and how it derives from graph structure, but does not standardize measurement protocols. Specifying operational procedures for measuring each component in each domain,  what instruments to use, what baselines to establish, how to isolate components,  would make cross-domain and cross-study comparison rigorous.

### Table K: Brooks's Law Derivation

| Team Size n | Isolated Work Capacity (linear) | Pairwise Coordination Edges | Coordination Cost (quadratic) | Net Throughput | Marginal Throughput of nth Member |
|------------|-------------------------------|---------------------------|------------------------------|---------------|----------------------------------|
| 1 | 1.0 | 0 | 0 | 1.00 | 1.00 |
| 2 | 2.0 | 1 | 0.10 | 1.90 | 0.90 |
| 3 | 3.0 | 3 | 0.30 | 2.70 | 0.80 |
| 4 | 4.0 | 6 | 0.60 | 3.40 | 0.70 |
| 5 | 5.0 | 10 | 1.00 | 4.00 | 0.60 |
| 6 | 6.0 | 15 | 1.50 | 4.50 | 0.50 |
| 8 | 8.0 | 28 | 2.80 | 5.20 | 0.30 |
| 10 | 10.0 | 45 | 4.50 | 5.50 | 0.10 |
| 11 | 11.0 | 55 | 5.50 | 5.50 | 0.00 (crossover) |
| 12 | 12.0 | 66 | 6.60 | 5.40 | −0.10 |
| 15 | 15.0 | 105 | 10.50 | 4.50 | −0.40 |
| 20 | 20.0 | 190 | 19.00 | 1.00 | −0.80 |

**Assumptions:** Each person contributes 1.0 unit of isolated work. Each coordination edge costs 0.10 units. Edges = n(n−1)/2. Coordination cost = edges × cost per edge. Net throughput = isolated − coordination. Crossover at n* ≈ 11 for these parameters.

**General formula:** n* = (1 + √(1 + 2/c_edge)) / 1, where c_edge is the coordination cost per pairwise edge. Lower c_edge (more efficient coordination) raises n*. Higher c_edge (expensive coordination) lowers n*.

**Note:** This model uses only the coordination component. Including contention (shared codebase, CI pipeline) and cascade (interruptions between team members) lowers n* further. The table represents a lower bound on tax.

### Key Equations Summary

**Resource utilization:**
ρ(rⱼ) = Σᵢ f(sᵢ, rⱼ) × h(sᵢ, rⱼ)

**Expected wait time (M/M/1):**
W(rⱼ) = ρ(rⱼ) / (μⱼ × (1 − ρ(rⱼ)))

**Contention cost:**
contention(sᵢ, G) = Σⱼ f(sᵢ, rⱼ) × W(rⱼ)

**Cascade cost:**
cascade(sᵢ, G) = Σⱼ≠ᵢ Σₖ κ(sᵢ, sⱼ, rₖ) × activity(sⱼ, rₖ) × recovery_cost(sᵢ)

**Coordination cost:**
coordination(sᵢ, G) = Σⱼ f(sᵢ, rⱼ) × coord(rⱼ)

**Blocking cost:**
blocking(sᵢ, G) = Σⱼ f(sᵢ, rⱼ) × c(sᵢ, rⱼ) × W(rⱼ)

**Interleave cost:**
interleave(sᵢ, G) = preemption_rate(sᵢ, G) × interleave_cost(active_streams(G))

**Total concurrency tax:**
tax(sᵢ, G) = contention + cascade + coordination + blocking + interleave

**In situ cost:**
cost_insitu(sᵢ) = cost_isolated(sᵢ) + tax(sᵢ, G)

**Tax discount:**
δ(expert, novice, G) = tax(expert, G) / tax(novice, G)

**Optimal stream count:**
n* = argmax_n { n × work_isolated − tax_total(n, G) }

**Brooks's Law crossover (complete graph, coordination only):**
n* = (1 + √(1 + 2/c_edge)) where c_edge = coordination cost per pairwise edge

**Fundamental inequality (from prior work, referenced throughout):**
Σ ops × d̄ ≤ N
